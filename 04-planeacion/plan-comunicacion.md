PLAN DE COMUNICACIÓN DEL EQUIPO – DEVBRAIN
1.1 Introducción
El presente documento describe el plan de comunicación utilizado durante el desarrollo del proyecto DevBrain, estableciendo los canales empleados, frecuencia de comunicación, responsables y herramientas utilizadas para mantener la coordinación del equipo durante los diferentes sprints.

1.2 Canales de Comunicación
Canal	Uso	Frecuencia	Responsables
WhatsApp	Comunicación diaria, reporte de avances, resolución de dudas y seguimiento asíncrono	Diario	Todo el equipo
Google Meet	Reuniones de seguimiento, revisión de avances y coordinación del equipo	Cierre de sprint y cuando fue necesario	Joseph
GitHub Issues	Registro, asignación y seguimiento de tareas	Durante todo el proyecto	Todo el equipo
GitHub Projects	Organización del backlog y visualización del avance del sprint	Actualización continua	Joseph y equipo
GitHub Pull Requests	Revisión e integración de cambios antes del merge	Por cada tarea completada	Responsables de módulo y revisores

 
1.3 Frecuencia de Comunicación
1.3.1 Daily asíncrono
El equipo utilizó WhatsApp como canal principal para mantener comunicación diaria y compartir avances del trabajo realizado.
•	Hice: Actividades completadas desde la última actualización. 
•	Haré: Actividades planeadas para continuar el desarrollo. 
•	Bloqueos: Problemas o dependencias que impedían avanzar. 
1.3.2 Reuniones de sincronización técnica
Se utilizaron reuniones mediante Google Meet para coordinar actividades técnicas, resolver dudas y revisar avances entre las diferentes áreas del proyecto.
Frecuencia:
•	Según necesidad del equipo. 
•	Principalmente durante revisiones y cierres de sprint. 
1.3.3 Sprint Review
Al finalizar cada sprint se realizó una reunión de revisión para analizar los avances obtenidos, problemas encontrados y acuerdos para el siguiente sprint.
Frecuencia:
•	Una reunión al cierre de cada sprint.

1.6 Política de Notificaciones y Pull Requests
•	Los cambios deben realizarse mediante ramas independientes. 
•	Los PR deben dirigirse hacia develop. 
•	Los cambios requieren revisión antes del merge. 
•	Responsables de módulo y al menos un integrante revisor.
•	GitHub debe revisarse periódicamente para evitar retrasos. 
•	Durante Sprint 2 se reforzó la revisión de la rama destino de los Pull Requests debido a cambios enviados incorrectamente hacia main en lugar de develop
1.7 Conclusión
El plan de comunicación permitió mantener organizado el desarrollo de DevBrain durante los cuatro sprints. El uso combinado de WhatsApp, Google Meet y las herramientas de GitHub facilitó la coordinación del equipo, el seguimiento de tareas y la integración de los diferentes módulos del proyecto.
